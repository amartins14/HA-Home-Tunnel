# Security

Home Tunnel makes a Home Assistant login page reachable from the public internet. Anyone who can reach the configured host can attempt to authenticate to Home Assistant. The tunnel does not replace Home Assistant authentication, MFA, user permissions, or security updates.

- Generate a unique 256-bit setup code in the Home Assistant app. Put its SHA-256 verifier in the IIS `web.config`; protect both the code and verifier as credentials. Keep the code in HA's private app data. HMAC challenge-response authenticates both sides without sending the code. The parties derive a separate permanent connector key, and the relay consumes the setup after finalization.
- Forwarding starts disabled. Enable it from the Home Tunnel app only after the connector is connected and the public endpoint has been reviewed. Disable it immediately if the connector or hosting account is compromised.
- Keep TLS valid and enable secure HTTP-to-HTTPS redirection at IIS or the upstream proxy.
- Do not expose the connector metrics listener or IIS `App_Data` publicly.
- The connector runs as an unprivileged UID, without HA/Supervisor APIs, host networking, or host mounts. It checks these runtime boundaries before connecting.
- Since 0.7.0 the app has Home Assistant API access (`homeassistant_api`), used only to list notify services and send notifications. `start.sh` passes the Supervisor token to the setup service under a private name; the service removes it from its environment, never passes it to the connector, and marks itself non-dumpable so the connector (same UID) can't read it through `/proc`. The connector refuses to start if it sees any Supervisor token. A compromise of the setup service itself would expose Home Assistant's API.
- Blocked addresses are kept in the app and sent to the relay, which answers them with 403 before anything reaches the connector. Automatic lockdown is on by default (20 denied answers or 15 login attempts in 10 minutes blocks an address for an hour) and never blocks an address that has signed in to Home Assistant. Home Assistant's own `ip_ban` can't help here: every tunneled request reaches Home Assistant from the app, so a ban there would block the whole tunnel.
- Country blocking relies on ipapi.co lookups made by the app, so it only works while caller locations are on, it sends each new public caller IP to ipapi.co, and it acts after a caller's first requests. Treat it as noise reduction, not a perimeter: VPNs and proxies change apparent country, and lookups stop for the day after 200 new addresses.
- Key rotation issues a new connector key from the relay; the old key keeps working until the app confirms the new one, then stops. Unpairing resets the relay's pairing state and block list; pairing again needs a new setup code and `web.config` hash. "Unpair only here" leaves the relay paired until `App_Data/home-tunnel-state.json` is deleted on the IIS host.
- WebSockets are allowed only to Home Assistant's `/api/websocket` and below an app web UI's ingress address (`/api/hassio_ingress/<session>/…`), which Home Assistant authenticates; both the relay and the connector enforce this, and refuse percent-encoded and dot segments. The relay enforces exact origin checks for browser WebSockets. Native clients are separately controlled by `HaTunnelNativeClientsEnabled` and default off. The relay keeps its last 20 refused WebSocket connections (time, caller IP, masked path, reason) in memory and shows them only to the paired app.
- The public IIS setup page is informational only. Pairing requires a high-entropy setup code generated inside the authenticated HA app. The relay applies rate limits and persists a one-time paired state before accepting the permanent connector key.
- The Home Assistant dashboard shows up to 20 recent requests with source IP, full sanitized path (without its query string), status, and duration. App web UI (ingress) session tokens and login-flow IDs are masked in every displayed path. A searchable caller list stores IP, request count, first/last seen, confirmed login time, and up to four short device labels (browser or app and operating system, derived from the User-Agent of WebSockets opened from that IP; the full User-Agent is not stored) privately for up to 30 days, capped at 2,048 addresses. **Clear history** clears this summary only. A separate rotating audit log also stores validated request IPs and paths, with a 10 MiB active file and up to four backups. *Signed in to HA* means the connector observed Home Assistant's `auth_ok` WebSocket message; *No sign-in seen* means no such confirmation was observed, and does not prove the caller failed to log in. Optional geolocation is off by default; when enabled, public caller IPs are sent to ipapi.co for an approximate city/region/country lookup. Results are cached in memory for 24 hours, with a 200-new-IP daily cap. IIS and hosting-provider logs are separate and may retain full URLs, IP addresses, and query strings; configure their access and retention deliberately.
- Caller IP is the address IIS sees. A reverse proxy in front of IIS can cause the logged address to be the proxy instead; Home Tunnel does not trust forwarded-IP headers.
- The relay host can see proxied Home Assistant traffic after TLS termination. Operate it on a trusted host and protect its deployment account.

Report vulnerabilities privately to the repository maintainer. Do not include live keys, session cookies, signed URLs, or unredacted logs in an issue.
